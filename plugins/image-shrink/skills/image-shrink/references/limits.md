# 实测限制与探测方法

测量时间：2026-10-12。测量方式：黑盒，直接对端点发请求，只看输入和返回。

## 结论

DeepSeek `https://api.deepseek.com/responses` 的**请求体上限 = 48 MiB（50,331,648 字节）**。
超过就返回 `413 Payload Too Large`。这个限制没有写进 DeepSeek 官方「错误码」文档
（官方只列了 400 / 401 / 402 / 422 / 429 / 500 / 503）。

## 原始数据

| 请求体字节数 | HTTP | 返回 |
| --- | --- | --- |
| 1,048,701 / 2,097,277 / 4,194,429 | 400 | 业务层参数校验错误（说明 body 被完整收下） |
| 8,388,733 / 16,777,341 / 33,554,557 | 400 | 同上 |
| 49,900,000 / 50,000,000 / 50,200,000 | 400 | 同上 |
| 50,331,600 / 50,331,648 | 400 | 同上 |
| **50,331,700** | **413** | `Failed to buffer the request body: length limit exceeded` |
| 67,108,989（64 MiB） | 413 | openresty 的 HTML 页 `413 Request Entity Too Large` |

`50,331,648 = 48 × 1024 × 1024`。所以是两层闸门：应用层 48 MiB，最外层 nginx 约 64 MiB。

## 探测方法（有个坑必须避开）

用「不存在的模型名」去探测是**无效的**：服务端可能一读到 `model` 字段就拒绝并挂断连接，
根本没读完请求体，于是不管发多大都显示"通过"。

正确做法是把请求构造成**服务端必须读完整个 body 才能报错**：

- `model` 用真实存在的名字
- 把非法参数（例如超出合法范围的 `max_output_tokens`）放在 JSON 的**最末尾**

这样服务端必然完整读取请求体，返回码才真实反映体积限制；同时参数校验失败，
不会真的跑推理，**不产生费用**。

脚本：`scripts/probe-body-limit.ps1`

## 图片体积换算

- 图片进请求体是 base64，体积 ≈ 源文件 × 1.33
- 每一轮请求都会重发历史里的全部图片，所以图片成本是**累积**的，不是一次性的
- 48 MiB ÷ 1.33 ≈ 36 MB：**一个会话里图片文件的累计总量到 35 MB 左右就会触顶**
- 触顶后该会话再也发不出请求，只能新开会话

压缩后的图通常在 100~400 KB，比原图小 5~20 倍。实测：1920x1080 的 6.23 MB PNG
→ 1280x720 的 0.35 MB JPEG（剩 6%）。
